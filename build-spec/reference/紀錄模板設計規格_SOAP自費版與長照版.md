# 紀錄模板設計規格 v1 — 自費 SOAP 版 × 長照申報版

*配合產品概念文件 v9 使用|設計原則:兩個模板、一層資料*

---

## 零、總架構:兩個模板,一層資料

```
           ┌─────────── 共用資料層 ───────────┐
           │ 個案基本資料|診斷與照會單|生命徵象 │
           │ 標準化測驗數據庫|SMART 目標庫      │
           │ 服務時間戳|照片|治療師簽章         │
           └──────┬──────────────┬──────────┘
                  │              │
        ┌─────────▼───┐   ┌──────▼──────────┐
        │ 長照申報模板  │   │ 自費 SOAP 模板   │
        │ 老闆=支審系統 │   │ 老闆=臨床品質+家屬│
        │ 目標=一次過核銷│   │ 目標=專業+可讀+AI │
        └─────────────┘   └─────────────────┘
```

**鐵律:任何資料只輸入一次。** 生命徵象、測驗數值、服務時間在共用層輸入,兩個模板各自取用;個案從長照轉自費(或並行)時,歷史數據無縫延續。

## 一、自費 SOAP 模板(本次設計重點)

### 設計原則
1. **結構化優先於自由文字**——結構化欄位餵趨勢圖、家屬儀表板、機構月報、AI 資料飛輪;自由文字只留給真正需要臨床敘事的地方
2. **S 和 A 偏敘事(+AI 輔助),O 和 P 偏結構化**——符合臨床思考的天然分工
3. **每個欄位標注三個屬性:** 必填/選填|結構化/自由文字|AI 輔助點

### S — Subjective 主觀

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| 個案/家屬主訴 | 自由文字 | ✅ | AI 輔助:語音轉文字直接落欄 |
| 疼痛 NPRS | 0–10 滑桿 + 部位選單 | ✅ | 結構化 → 自動趨勢圖 |
| 自覺疲勞(Borg RPE) | 6–20 選單 | 選填 | 運動處方強度校準用 |
| 居家運動執行回報 | **自動帶入** | 自動 | **連動病患端 AI 影像日誌**:上次至今的執行次數、影片摘要自動彙入,治療師勾選確認——這是雙模板架構裡自費版獨有的殺手欄位 |
| 睡眠/胃口/情緒異常 | 快速勾選 + 備註 | 選填 | 異常時觸發 A 段風險提示 |

### O — Objective 客觀

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| 生命徵象(BP/HR/SpO₂) | 數值(共用層) | 條件必填 | 心血管風險個案強制;超出安全區間自動紅字 |
| 標準化測驗 | **測驗庫選單 + 數值** | 每 2–4 週至少一項 | 內建:TUG、30 秒坐站、BBS、步速(4m/10m)、SPPB、握力、單腳站、MMSE 等;輸入數值自動比對常模與跌倒風險切點,自動畫趨勢 |
| 觀察紀錄 | 半結構(部位/動作品質標籤 + 短述) | ✅ | 標籤化供日後檢索(例:「站起代償」「步態不對稱」) |
| 治療介入 | **結構化清單** | ✅ | 每項 = 介入類別(操作/運動/功能訓練/衛教)+ 動作名稱(動作庫選單)+ 劑量(組×次×阻力/時間);動作庫與病患端 HEP 影片庫同源 |

### A — Assessment 評估

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| 與 SMART 目標對照 | **目標庫連動** | ✅ | 每個進行中目標顯示基準值→本次值→目標值,系統自動算達成 %;治療師只需判讀,不用翻舊紀錄 |
| 臨床判讀 | 自由文字 | ✅ | **AI 輔助核心點:** 依 S+O 結構化資料生成判讀草稿,治療師修改定稿——「AI 版 vs 修正版」配對即資料飛輪(概念文件第十章) |
| 進展標記 | 進步/維持/退步 三選一 | ✅ | 餵家屬儀表板與機構月報 |
| 風險註記 | 勾選(跌倒/心血管/皮膚/吞嚥/其他) | 條件必填 | 勾選即要求對應處置寫入 P |

### P — Plan 計畫

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| 下次治療重點 | 短述 | ✅ | 下次開單時自動帶入提醒 |
| 居家運動處方(HEP) | **動作庫勾選 + 劑量** | ✅ | 勾選即推送到病患端(附示範影片),病患拍攝回報 → 回流到下次 S 段——**SOAP 的 P 和 S 在平台上閉環** |
| 頻率/療程調整 | 選單 | 選填 | 變更時自動通知家屬端 |
| 轉介/照會建議 | 選單 + 備註 | 選填 | 勾選「需回診」時可連動診斷證明流程指南 |

### 法遵掛鉤(自費版必備,寫死在模板)
- **照會單編號欄**:兩軌制——「治療目的」個案必填照會單/醫囑編號;「非治療目的」(運動指導)選填但須勾選聲明,憑證同步走發票軌(概念文件第十三章憑證兩軌)
- 服務起訖時間戳 + 到宅照片(選填)——醫糾舉證鏈
- 告知同意書連結狀態顯示
- 紀錄一經簽章鎖定,修改留版本軌跡——保存十年、防偽造文書質疑

### 雙版本輸出(這個模板最重要的產品設計)
每份 SOAP 定稿後自動生成兩個視圖:
1. **專業版**——完整 SOAP,給督導稽核、同業轉介、法規保存
2. **家屬版**——AI 將 SOAP 轉譯為白話摘要(今天做了什麼、進步在哪、回家要做什麼),掛治療師名字推送到家屬儀表板

*家屬版轉譯規則:數據視覺化優先(TUG 從 18 秒進步到 14 秒 → 一張趨勢圖)、禁用術語(「髖屈曲攣縮」→「髖部緊繃影響站直」)、永遠以「接下來怎麼做」收尾。這是治療師的隱形口碑行銷(第九章),也是進階方案的付費理由。*

## 二、長照申報模板(對照設計,較簡)

**設計目標只有一個:一次過核銷。** 欄位 = 照管系統申報必填欄 + 專業服務要求,不多不少:

| 區塊 | 欄位 | 對應 |
|------|------|------|
| 申報核心 | 服務日期、起訖時間(邏輯檢核防 14:00~14:00)、服務項目代碼(CA07/CC01)、服務人員(自動帶認證職類)、服務數量 | FA100 申報欄位,預檢引擎逐項檢查 |
| 專業服務 | 照顧目標(目標庫連動)、本次目標執行內容、完成度、個案/家屬回饋 | 專業服務紀錄與查核要求(FA-400 情境自動偵測) |
| 佐證 | 時間戳、照片、簽章 | 突襲查核與偽造文書防線 |
| 匯出 | QD110 批次匯入格式/未來介接直傳 | 概念文件第七章核銷自動化 |

**與 SOAP 版的共用點:** 目標庫、測驗庫、生命徵象都是同一層資料——長照個案的 BBS 分數和自費個案存在同一個數據庫,轉軌零遷移。

**刻意不做的事:** 長照模板不強制 SOAP 敘事結構。核銷不需要、查核不需要、治療師的時間更不需要;想寫深度臨床紀錄的治療師可以在同一個案上「加開」SOAP 紀錄(選用),兩者並存不互斥。

## 三、兩模板的分流規則

| 情境 | 用哪個模板 |
|------|-----------|
| 照管派案(CA07/CC01) | 長照申報模板(必用) |
| 平台媒合自費個案 | SOAP 模板(必用) |
| 長照個案自費加購次數 | SOAP 模板 + 標記「自費」(QD110 匯入時自動排除於 FA100 申報——照管系統本就不收自費紀錄) |
| 機構合作案(據點/日照) | SOAP 簡化版 + 五類品質指標欄 → 餵機構月報 |

## 四、開發優先序建議

1. **共用資料層 + 長照申報模板**(核銷是治療所的生存線,先做)
2. **SOAP 模板之結構化欄位**(S 的 NPRS、O 的測驗庫與介入清單、P 的 HEP)——不含 AI
3. **家屬版自動轉譯**(第一個 AI 功能,價值最直觀、技術最成熟)
4. A 段判讀草稿生成(資料飛輪正式啟動)
5. 病患端影像日誌 ↔ S 段回流閉環

## 五、自費快速模式:重新定位 v1 自費模板

### 5.1 核心洞察:自費診所要的不是「更完整」,是「更快」

v1 的自費 SOAP 模板針對的是「臨床品質+家屬溝通+AI 資料飛輪」,欄位設計偏向完整。但參考同類自費工具的共通打法後,浮現一個更貼近**高量體徒手治療診所**實際工作型態的需求:一天看 10–15 位個案、每位 50 分鐘治療只能擠出 2–3 分鐘寫紀錄,**多一個欄位就是多一份治療師不想用系統的理由**。

所以 v2 把自費模板拆成兩層,治療師可自行切換:

| | 快速模式(v2 新增) | 完整模式(v1 既有) |
|---|---|---|
| 定位 | 日常高量體回診 | 初評、複雜個案、需深度臨床推理時 |
| 完成時間目標 | ≤90 秒 | 3–5 分鐘 |
| S/A 段 | 快速勾選+語音一句話 | 結構化+AI 判讀草稿 |
| O/P 段 | 沿用上次+差異點修改 | 完整重新輸入 |
| 適用情境 | 90% 的回診 | 初評、療程中期評估、結案 |

**兩者共用同一層資料**(第零章的共用資料層不變),差別只在**輸入介面的摩擦力**,不是資料模型的深淺——這樣治療師在忙碌診間用快速模式,系統背後累積的還是同一套結構化數據,不會犧牲 AI 資料飛輪或家屬儀表板的品質。

### 5.2 快速模式介面設計原則

**「複製上次治療」是核心機制。** 徒手治療的回診高度重複(同個案、相近的介入手法、漸進的劑量調整)——開啟本次紀錄時,系統預設帶入上次的 O 段介入清單與 P 段 HEP 處方,治療師只需**修改差異點**(這次多做了什麼、少做了什麼、劑量變化),而非從空白開始。這是把「寫紀錄」變成「校對紀錄」,是效率的最大槓桿。

**快速勾選優先於打字。**
- 疼痛 NPRS:滑桿,非輸入數字
- 介入項目:常用手法/運動做成個人化「常用清單」(治療師自訂,置頂顯示),點選即完成,不用每次從完整動作庫搜尋
- 身體部位標記:人形圖點選部位(比文字輸入「右肩」更快,也更適合觸控螢幕)

**語音一句話補充,不是語音聽打全文。** 不做即時語音轉整段病歷(通話式聽打容易斷線、口誤多、事後編輯成本高),改成**針對單一欄位的短語音**:按住麥克風說一句話(例如主訴或本次重點),AI 轉文字直接落欄——範圍小、準確度高、不需要事後大幅修改。

**當下完成、當下簽章。** 治療結束、個案還在現場時就能完成紀錄(不是回家再補),簽章鎖定後,家屬版摘要立即可推送——治療師走出治療室,紀錄已經寫完。

**行動裝置與現場情境優先。** 介面預設為平板直向單手操作(治療師常一手扶個案、一手操作);字體與按鈕尺寸比長照模板更大,減少誤觸。

### 5.3 快速模式與長照模式的關係(呼應第零章架構)

快速模式解決的是「自費診所的效率」,長照模板解決的是「核銷合規」——**兩者不衝突,是同一個治療師依情境切換的兩個入口**:

```
                治療師開啟一筆紀錄
                        │
              ┌─────────┴─────────┐
              │ 這是長照派案個案?   │
              └─────┬───────┬─────┘
                    是            否(自費)
                    │             │
              長照申報模板    ┌────┴────┐
              (v1 第二章,    │ 快速模式? │
               不變)         └────┬────┘
                             是        否
                             │         │
                        90 秒快速   完整 SOAP
                        (5.1-5.2)   (v1 第一章)
```

同一個治療師一天之內,長照個案走申報模板、自費回診走快速模式、自費初評走完整模式——三種入口共用同一層資料,這正是第零章「一層資料」設計在今天派上用場的地方。

## 六、病歷系統一鍵轉換架構

### 6.1 台灣市場現況(誠實評估,決定架構方向)

查證後的結論:**自費徒手治療所這個市場沒有主流的病歷系統品牌可以綁定。** 與美國(WebPT、Cliniko 等少數幾家寡占)不同,台灣的狀況是:

- 部分診所使用一般診所雲端 HIS(如國際厚生等,主要服務健保診所,非 PT 專用)
- 部分使用預約管理系統附加病歷功能(如 SimplyBook.me 有「SOAP 病歷紀錄」客製功能)
- 相當比例是 **Excel/Google Sheets 手工管理**,或甚至紙本
- 政府的長期方向是 **HL7 FHIR** 全國病歷互通(電子病歷交換中心、次世代電子病歷計畫),但目前僅推進到醫院層級,尚未下探到小型自費診所

**這個現實直接決定架構原則:不要賭死綁定特定品牌 API(可能綁了也沒幾家診所在用),改採格式導向、分層涵蓋的匯入精靈。**

### 6.2 三層匯入策略

| 層級 | 適用情境 | 技術方式 | 涵蓋率預估 |
|------|---------|---------|-----------|
| **第一層:結構化匯入(優先開發)** | 診所用 Excel/Google Sheets 或系統可匯出 CSV | **欄位對應精靈**:上傳檔案→系統自動偵測欄位→人工確認/調整對應關係→匯入預覽→確認 | 最大宗,預估涵蓋六至七成有電子紀錄的診所 |
| **第二層:PDF/掃描辨識** | 系統只能匯出/列印 PDF,或診所本身是紙本病歷 | 上傳 PDF 或拍照→OCR 文字辨識→AI 抽取關鍵欄位(姓名、生日、病史、SOAP 重點)→人工逐筆確認 | 涵蓋紙本與封閉系統診所;準確度較低,**必須保留人工確認步驟,不可全自動匯入** |
| **第三層:FHIR API 介接(長期布局)** | 未來若診所系統支援 FHIR 標準(政府推動方向) | 標準化 API 直接串接 | 目前涵蓋率低,但**與概念文件第七章「照管平台自建系統介接」同一個技術方向**,及早布局有綜效 |

**優先順序:先做第一層。** 理由:開發成本最低、涵蓋率最高、準確度最有把握(比 OCR 可靠),而且大部分診所(即使用專屬系統)通常都能匯出 Excel/CSV 作為備份——這是最務實的第一步。

### 6.3 匯入精靈使用者流程(第一層,MVP 範圍)

```
Step 1  上傳檔案(拖拉 Excel/CSV,或貼上 Google Sheets 連結)
Step 2  系統自動掃描欄位標題,嘗試比對常見欄位名稱
        (例:「姓名」「病患姓名」「Name」→自動對應「個案姓名」)
Step 3  人工確認畫面:左側顯示偵測到的原始欄位,右側下拉選單
        對應到平台欄位;無法自動比對的欄位,人工手動指定或標記「不匯入」
Step 4  預覽前 5 筆資料,確認對應正確
Step 5  執行匯入;錯誤列(如生日格式錯誤)列出清單供人工修正後重新匯入
Step 6  匯入完成報告:成功筆數、失敗筆數、失敗原因
```

**欄位對應表(建議 MVP 涵蓋範圍):**

| 平台欄位 | 常見原始欄位名稱(自動比對關鍵字) | 必要性 |
|---------|------------------------------|--------|
| 個案姓名 | 姓名、病患姓名、Name、患者 | 必要 |
| 出生日期 | 生日、出生日期、DOB | 必要 |
| 聯絡電話 | 電話、手機、聯絡方式 | 建議 |
| 初診日期 | 初診、建檔日期、First Visit | 建議 |
| 主要診斷/主訴 | 診斷、主訴、Diagnosis、Chief Complaint | 建議 |
| 病史備註 | 病史、既往史、備註、Note | 選填(併入自由文字欄) |
| 過去治療紀錄 | SOAP、治療紀錄、Progress Note | 選填(整段併入歷史紀錄區,供人工日後回顧,不強制結構化拆解) |

**設計原則:寧可少匯入結構化欄位、把不確定的內容整段放進「歷史備註」區保留原文,也不要錯誤拆解造成資料失真。** 結構化程度可以之後在平台上逐步補齊,但錯誤的結構化資料會誤導臨床判斷,風險更高。

### 6.4 法遵與資料品質責任(重要,不可省略)

- **個資移轉同意:** 診所將既有病患資料匯入平台,須有患者同意移轉之法律基礎(通常併入平台使用條款的個資告知,或由治療所另行取得既有個案之同意);比照第十三章委託處理關係辦理
- **資料正確性由治療師確認,非系統自動保證:** 匯入精靈的角色是降低輸入摩擦,不是取代臨床判斷——尤其第二層 OCR 辨識,匯入完成後應提示「請於首次接觸個案時核對關鍵資料(過敏史、禁忌症等)」
- **長照個案的既有 C 碼紀錄不透過此精靈匯入:** 長照申報紀錄之來源是照管系統本身(見第七章 QD110 介接),此匯入精靈僅處理**自費個案**的既有病歷遷移,兩條資料來源分開,避免混淆申報資料完整性

## 七、產品與商業意義

**一鍵轉換是治療師招募的摩擦力移除器。** 回顧借鑑改進提案清單(L9 招募頁「以終為始」),治療師猶豫加入新平台的常見原因之一是「我原本的個案資料要重新登打」——這正是任何工具轉換的天然阻力。匯入精靈把「換平台的代價」從「幾十小時的重新登打」降到「上傳一個 Excel、確認幾個欄位對應」,直接提升招募轉換率。

**快速模式是留客機制,不只是效率工具。** 對照第十二章防跳單設計,治療師留在平台的理由之一是「工具好用捨不得走」——如果自費快速模式真的能把日常回診紀錄壓到 90 秒,這件事本身就是黏著力,比任何條款都有效。

**與 Luna/家天使的差異化再確認。** 競品排查報告指出 Luna 的 Auto-Charting 是通用病歷語音轉寫;我們的快速模式額外做了「複製上次治療」與「個人化常用清單」——這兩個機制更貼近徒手治療高重複性回診的實際工作型態,是通用型 AI 聽打工具做不到的專科深度。

1. **訪談時加一題(併入 B6 同業訪談):** 「你現在用什麼系統或方式記錄病患資料?(Excel/專屬系統/紙本/其他)」——這題的答案會直接校準第一層匯入精靈的欄位對應規則庫,是目前唯一能把「格式導向」設計落地成「準確涵蓋大多數診所實際狀況」的方式
2. **OCR 服務供應商評估:** 第二層 PDF/掃描辨識需選定 OCR/AI 抽取服務(可用主流雲端 OCR API),成本與準確度待實測樣本校準(建議先用團隊自己診所的病歷做一輪測試)
3. **FHIR 介接時程:** 與第七章「照管平台自建系統介接」的技術布局能否共用同一組開發資源與時程,待技術規劃階段評估
