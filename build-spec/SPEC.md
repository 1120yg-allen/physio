## 一、系統總架構

```
┌─────────────── 共用資料層(Single Source of Truth)───────────────┐
│  個案主檔 │ 診斷與照會單 │ 生命徵象 │ 標準化測驗庫 │ 目標庫        │
│  服務時間戳 │ 照片 │ 簽章與版本軌跡 │ 動作庫(HEP)                  │
└───────┬──────────────────────────────────┬───────────────────────┘
        │                                  │
┌───────▼──────────┐              ┌────────▼─────────────────────┐
│  長照申報模板      │              │  自費 SOAP 模板               │
│  目標 = 一次過核銷  │              │  完整模式 / 快速模式(90 秒)   │
│  → QD110 匯出     │              │  → 專業版 + 家屬版雙輸出       │
└──────────────────┘              └──────────────────────────────┘
```

**鐵律:任何資料只輸入一次**(CLAUDE.md C5)。

### 2.3 SoapNote(自費紀錄,1:1 對應 Encounter)

```
subjective: {
  chief_complaint: text,          // 主訴(可語音)
  npre: { score: 0-10, site: string[] },
  borg_rpe: int?,                 // 6-20
  hep_adherence: {                // 自動帶入上次 P 段處方的執行回報
    prescribed: ExerciseRef[],
    reported_sessions: int,
    note: text
  },
  flags: { sleep: bool, appetite: bool, mood: bool, note: text }
}

objective: {
  vitals: { bp_s, bp_d, hr, spo2 },     // 共用資料層
  measures: [{ test_id, value, unit, measured_at }],  // 測驗庫
  observations: [{ region, quality_tag[], note }],
  interventions: [{                      // 結構化介入清單
    category: manual|exercise|functional|education,
    item_id,                             // 動作庫
    dose: { sets, reps, resistance, duration }
  }]
}

assessment: {
  goal_progress: [{ goal_id, baseline, current, target, pct }],
  clinical_reasoning: text,
  trend: improving|maintaining|declining,
  risk_flags: fall|cardiac|skin|swallowing|other[]
}

plan: {
  next_focus: text,
  hep: [{ item_id, dose, video_ref }],   // 推送至家屬/個案端
  frequency_change: text?,
  referral: text?
}
```

| 表 | 內容 |
|---|---|

## 三、自費 SOAP 模板

### 3.1 兩種模式

| | 快速模式 | 完整模式 |
|---|---|---|
| 適用 | 日常回診(約 90% 情境) | 初評、複雜個案、療程中期評估、結案 |
| 目標時間 | **≤ 90 秒** | 3–5 分鐘 |
| S/A | 快速勾選 + 單句語音 | 完整結構化輸入 |
| O/P | **沿用上次 + 只改差異點** | 完整重新輸入 |

兩者**共用同一資料模型**,差別只在輸入介面摩擦力,不犧牲資料結構完整度。

### 3.2 快速模式的四個核心機制

1. **複製上次治療**——開啟新紀錄時預設帶入上次的 O 段介入清單與 P 段 HEP;治療師只修改差異點。把「寫紀錄」變成「校對紀錄」,這是效率最大槓桿。
2. **點選優先於打字**——NPRS 用滑桿;介入項目用個人常用清單置頂;部位用人形圖點選。
3. **單句語音,非整段聽打**——按住麥克風說一句話落入單一欄位。不做即時通話式整段轉錄(斷線風險高、事後編輯成本大)。階段一直接用 iOS 鍵盤聽寫。
4. **當場完成、當場簽章**——治療結束、個案還在現場時即完成紀錄,簽章後家屬版摘要立即可推送。

### 3.3 介面要求

- 預設**平板直向單手操作**(治療師常一手扶個案)
- 字體與按鈕尺寸大於長照模板,減少誤觸
- 每次開啟紀錄,**禁忌症與注意事項必須顯示在最上方**

### 3.4 雙版本輸出

每筆簽章後自動產生兩個視圖:

| | 專業版 | 家屬版 |
|---|---|---|
| 內容 | 完整 SOAP | 白話摘要:今天做了什麼、進步在哪、回家要做什麼 |
| 用途 | 督導稽核、同業轉介、法規保存 | 推送家屬儀表板/LINE |
| 轉譯規則 | — | 數據視覺化優先(TUG 18→14 秒畫趨勢圖);禁用術語(「髖屈曲攣縮」→「髖部緊繃影響站直」);**永遠以「接下來怎麼做」收尾** |

## 四、長照申報模板與核銷預檢引擎

### 4.1 制度時序(系統硬約束)

- 當月紀錄**隔月**上傳(10 月紀錄 11/1 起才可 FA100)
- FA100 後 20–30 分鐘且狀態=傳輸完成,才可 FA110;FA110 每次查詢須間隔 30 分鐘
- 紀錄修正後須隔 **1 小時**才能重傳
- 待申報紀錄僅保留服務日期**近 6 個月**,逾期系統排程刪除

> **退件一次的代價:上傳 → 等 30 分 → 查詢 → 發現錯誤 → 修正 → 隔 1 小時 → 重傳。一筆錯誤燒掉半天。**
> 這就是預檢引擎的價值來源。

### 4.2 預檢引擎(上傳前本機檢查,對應官方常見退件原因)

| # | 檢查項 | 規則 |
|---|---|---|
| 1 | 額度檢查 | 申報金額/次數 ≤ 個案當月分配額度餘額 |
| 2 | 特約有效期間 | 服務日期落於特約起訖內 |
| 3 | 人員資格 | 服務人員認證登錄與職類相符(長照 Level 綁定) |
| 4 | 計畫有效區間 | 服務日期在照顧計畫有效期間內 |
| 5 | 暫停服務區間 | 服務日期不落於個案暫停期間 |
| 6 | 時間邏輯 | 起訖時間合理,end > start |
| 7 | 重複申報偵測 | 同個案同日同代碼不得重複 |
| 8 | 中途結案偵測 | 觸發 FA400 前置提醒 |

**每項檢查都要有單元測試。** 這是全系統法遵風險最高的模組。

### 4.3 核銷月曆與狀態追蹤

- 每月 1 日自動提醒上傳
- 總表狀態機視覺化(卡在哪一關一目瞭然)
- **6 個月死線倒數警示**
- 額度餘額儀表板:接近上限時提前提示,把「要額度」從被動變主動

### 4.4 匯出

- 階段一:**QD110 批次匯入格式**匯出(平台登打一次、照管系統零重打)
- 階段二(長期):申請照管平台「民間自建系統」介接,每日同步 + 次月直接申報
- ⚠️ QD110 匯入之**自費個案不列入 FA100 申報**——匯出時自動排除自費紀錄

## 五、排程與行事曆

- 本機排程表:日/週檢視,顯示個案、地點、軌別、時段
- 排程 → 紀錄一鍵連動(從行程直接開該次 Encounter)

- 路線順序提示:同日多個到宅行程依地址排序(**不做自動路徑規劃,僅提示順序**)

| 功能 | 說明 |

## 七、病歷資料匯入(三層策略)

| 層級 | 適用 | 方式 | 優先序 |
|---|---|---|---|
| 第一層 | Excel / CSV / Google Sheets | **欄位對應精靈**:上傳 → 自動偵測欄位 → 人工確認對應 → 預覽前 5 筆 → 匯入 → 錯誤清單 | ✅ 先做 |
| 第二層 | PDF / 紙本掃描 | OCR + AI 抽取 → **強制人工逐筆確認** | 後期 |
| 第三層 | FHIR API | 標準化介接 | 長期布局 |

**台灣市場現況:自費物治所無主流病歷系統品牌可綁 API**,多為 Excel、預約系統附加病歷、或紙本。因此架構採格式導向,不賭死特定廠商。

**設計原則:寧可少匯入結構化欄位、把不確定內容整段存進「歷史備註」保留原文,也不要錯誤拆解造成資料失真。**

## 八、備份與資料保全

- SQLite 單檔,每日自動備份至 NAS
- **異地或離線備份必備**——單一 NAS 有勒索軟體與火損的單點風險,不可作為唯一保存
- 磁碟加密、帳號權限控管、存取紀錄留存
- 此等措施同時滿足:個資法安全維護義務、營業秘密法「保密措施」要件、長照查核佐證——一套投資三重效益

## 九、不在本期範圍(明確排除)

| 項目 | 理由 |
|---|---|
| 治療師媒合平台 | 需先有治療師網絡;方案 C 起步階段不做 |
| 回饋金商城 / 課程媒合 | 商業模式後期功能 |
| AI 動作辨識計數 | 技術難度與成本高,辨識不準會摧毀信任 |
| 自動判讀 / 風險警示 | 可能被認定為醫療器材軟體 |
| 多治療師帳號與派案系統 | 單人階段不需要 |

以上任何一項若要納入,**先問使用者**,不要自行擴大範圍。
